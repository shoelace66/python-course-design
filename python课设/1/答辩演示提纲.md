# MusicScope 音乐特征分析器——5 分钟答辩演示提纲

## 一、答辩前准备

1. 确认电脑安装 Python 3.10 或更高版本。
2. 双击 `一键启动.bat`，确认浏览器能够打开 MusicScope。
3. 预先运行一次 `一键运行测试.bat`，确认显示 `Ran 7 tests ... OK`。
4. 数据库中保留 2～3 条不同分类的记录，使概览页和筛选功能有内容。
5. 准备一份刚导出的完整 JSON，必要时用于导入演示。
6. 关闭无关窗口和通知，浏览器缩放建议保持 100%。
7. 演示优先使用系统内置 C 大调、120 BPM 音频，避免现场音频格式不兼容。

如果现场端口 8765 被占用，应以启动窗口打印的新地址为准。演示期间不要关闭启动 MusicScope 的终端窗口。

## 二、5 分钟演示流程

### 0:00～0:30 开场：说明问题与完成目标

建议讲稿：

> 我的课程设计题目是 MusicScope 音乐特征分析器。它可以从 WAV 音频中提取节奏、音调、音量和频谱特征，进行可视化和可解释分类。系统有完整的 Web 图形界面，所有分析指标和绘图序列都会保存到 SQLite，并支持 JSON、CSV 和数据库备份，以及 JSON/CSV 重新导入。整个后端只使用 Python 标准库，可以离线一键运行。

页面操作：停留在“数据概览”，指出累计分析、总时长、平均 BPM、平均响度、分类分布和最近记录。

### 0:30～1:05 总体架构与技术选择

切换到“原理与帮助”页，指向顶部流程。

建议讲稿：

> 系统采用本地浏览器加 Python HTTP 服务的结构。浏览器负责界面和 Canvas 图表；Python 负责 WAV 解码、FFT、自相关和 SQLite；音频不发送到互联网。这样既满足图形界面要求，也不需要安装 Flask、NumPy 或 librosa。代码分为 audio、database、server 和原生前端四部分。

必须点到的关键词：

- `ThreadingHTTPServer`
- PCM WAV
- 原生 Canvas
- SQLite
- 本地离线

### 1:05～2:35 核心演示：生成、分析和可视化

操作顺序：

1. 进入“音乐分析”。
2. 点击“没有音频？生成演示”。
3. 等待进度到 100%。
4. 从上到下展示指标和图表。

建议讲稿：

> 为了使答辩结果可重复，我设计了一个内置演示音频。程序会生成 C 大调、120 BPM 的单声道 PCM WAV，然后走与用户上传完全相同的分析和入库流程。

分析完成后依次说明：

- **节奏：** 短时 RMS 能量上升沿形成起音包络，再通过自相关寻找周期，换算 BPM。
- **音调：** 对有效帧做归一化自相关得到主导基频，再按十二平均律转换为 A4、C4 等音名。
- **调性：** FFT 频点聚合为 12 个 Chroma 音级，再与 24 个大小调模板比较。
- **音量：** 直接从原始 PCM 计算 RMS dBFS 和峰值，保留音频真实数字幅度差异。
- **分类：** 综合 BPM、响度、频谱重心和动态范围，并显示判断依据；它是规则匹配度，不冒充机器学习概率。
- **图表：** 波形、RMS 能量、64 个频带的平均频谱、十二音级能量。

可以读出一个实际结果，但不要保证每次 BPM 必须恰好等于 120；纯算法估计可能有少量误差。

### 2:35～3:15 数据库持久化与历史恢复

操作顺序：

1. 进入“分析记录”。
2. 搜索刚才演示文件名中的“演示音频”。
3. 按分类筛选一次。
4. 点击“查看”，恢复完整图表。

建议讲稿：

> 一次分析会在同一事务内写入 tracks、analyses、features 和 classifications。features 中不仅有摘要指标，还把压缩后的波形、能量、频谱和 Chroma 序列保存为 JSON。因此从历史记录点“查看”时，图表直接从 SQLite 恢复，不需要重新分析。外键使用级联删除，数据库记录和本地音频可以保持一致。

如时间紧张，只完成“查看”操作即可，不要现场删除主要演示记录。

### 3:15～3:55 导入导出闭环

进入“数据管理”。

建议讲稿：

> 系统实现了三种输出。完整 JSON 包含指标、分类和图表序列，可以重新导入；CSV 使用 UTF-8 BOM，适合 Excel 查看，但只保存摘要；SQLite 备份使用数据库在线备份接口生成一致副本。导入时逐条校验，同一文件哈希和分析时间的记录自动跳过，单条错误不会影响其他合法记录。

现场至少点击一次“下载完整数据”，让浏览器出现下载记录。若时间充足，再选择预先准备的 JSON 导入，并指出“成功、跳过重复、失败”提示。

注意：JSON、CSV 和数据库备份都不包含 `data/uploads` 中的原始 WAV；导入记录可以查看指标，完整 JSON 可以恢复图表，但通常不能试听。

### 3:55～4:30 算法公式与可解释性

回到“原理与帮助”，重点讲三个公式：

1. 响度：`dBFS = 20 log10(RMS)`。
2. 节奏：`BPM = 60 × frame_rate / lag`。
3. 音高：`MIDI = 69 + 12 log2(f / 440)`。

建议讲稿：

> 这三个公式分别把采样振幅变成数字响度、把自相关周期变成每分钟节拍数、把频率变成音乐音名。频谱部分使用 Hann 窗和自主实现的 1024 点 Cooley-Tukey FFT。所有方法都能在源码中逐步追踪，符合课程设计强调原理和实现过程的要求。

### 4:30～5:00 测试与总结

可切到已经运行完成的测试窗口，或口头展示测试结果。

建议讲稿：

> 项目共有 7 项标准库 unittest。4 项音频测试分别验证 440 Hz A4、演示音乐完整特征、损坏 WAV 错误处理，以及静音不崩溃并分类为“静音或近静音”；2 项数据库测试验证数据往返和 SQLite 备份；1 项服务器测试验证完整 HTTP 流程，并断言 Range 音频请求返回 206。目前 7 项全部通过。项目已经完成图形界面、音乐分析、可视化与分类、数据库保存、导入导出的完整闭环。当前主要限制是只直接支持 PCM WAV，后续可以接入 FFmpeg 和机器学习分类。

## 四、常见提问与参考回答

### 1. 为什么选择 Web 界面，而不是 Tkinter？

浏览器同样是图形用户界面。原生 HTML/CSS 更便于构建响应式布局，Canvas 适合绘制波形和频谱。后端使用 Python 标准库本地服务，仍然是一个完整的 Python 项目，而且不需要安装桌面 GUI 组件。

### 2. 为什么没有使用 librosa、NumPy 或 Flask？

本项目优先考虑课程展示中的可部署性和算法可解释性。只要安装 Python 3.10 就能运行，不受实验室电脑网络和包版本影响。FFT、自相关、PCM 解码等关键过程由源码实现，便于说明原理。代价是速度和专业鲁棒性低于经过优化的第三方库。

### 3. 为什么目前只支持 PCM WAV？

Python 标准库的 `wave` 模块稳定支持未压缩 PCM WAV，而 MP3、M4A 和 AAC 需要额外解码器。项目选择可控输入以保证零依赖和现场稳定性。目前支持 8/16/24/32 位、1～8 声道、4 kHz～384 kHz 的 PCM WAV。其他格式可先转换为 WAV，后续也可接入 FFmpeg。

### 4. BPM 是怎样计算的？

先计算每帧 RMS，把能量上升部分形成起音包络，再计算起音包络的自相关。最高相关峰对应重复节拍的帧延迟，利用 `BPM = 60 × frame_rate / lag` 换算。搜索范围约为 55～200 BPM，并加入常见音乐速度的轻微先验。

### 5. 为什么检测结果可能是实际 BPM 的一半或两倍？

音乐的强拍、弱拍和细分节拍都具有周期性，自相关可能把小节周期或八分音符周期当作主要周期，形成半拍/双拍误差。本项目用速度范围和轻微先验降低这种情况，但不能完全消除。专业系统通常还会使用多候选跟踪和节拍动态规划。

### 6. 音高和调性有什么区别？

音高是帧级基频，回答“主要声音大约是多少 Hz、接近哪个音名”；调性是整段音乐中 12 个音级的整体关系，回答“更接近哪个大调或小调”。本项目的音高使用归一化自相关，调性使用 Chroma 与 24 个大小调模板相关匹配。

### 7. 为什么 440 Hz 会得到 A4？

十二平均律规定 A4 为 440 Hz。用 `MIDI = round(69 + 12 log2(f/440))`，当 `f=440` 时得到 MIDI 69，对应 A4。自动测试也专门合成了 440 Hz 正弦波验证这一点。

### 8. 音量为什么使用 dBFS？

WAV 采样是数字幅度，没有经过麦克风和声压计标定，因此适合使用相对于数字满刻度的 dBFS。公式为 `20 log10(RMS)`。它能比较数字文件自身的幅度，但不能解释为真实环境中的分贝声压级，也不是 LUFS。

### 9. 为什么计算音量前不能整体归一化？

整体归一化会把不同文件的峰值都拉到相同水平，原来的音量差异会丢失。因此项目直接用原始解码幅度计算 RMS、峰值和动态范围，只在绘制某些相对曲线时做归一化。

### 10. FFT 在项目中有什么作用？

FFT 把时域采样转换为频域幅度，用于平均频谱、频谱重心、85% 滚降点和 Chroma。项目使用 Hann 窗降低帧边界频谱泄漏，并自主实现 1024 点基 2 Cooley-Tukey FFT，复杂度约为 `O(N log N)`。

### 11. 分类是不是机器学习？准确率是多少？

不是。当前是版本化的可解释规则分类，综合 BPM、RMS dBFS、频谱重心和动态范围，输出听感倾向及命中理由。界面称为“规则匹配度”，没有把它说成机器学习概率。因此不能给出数据集上的分类准确率；若要升级为机器学习，需要先准备有代表性的标注数据并划分训练集、验证集和测试集。

### 12. 数据库如何满足课程要求？

系统使用 SQLite，设置 `tracks`、`analyses`、`features`、`classifications` 等表。一次分析的元数据、指标、分类和可视化序列都入库；重新启动后历史仍存在。系统可导出完整 JSON、CSV 摘要和 SQLite 备份，也可以把 JSON/CSV 重新导入数据库，形成完整往返。

### 13. 为什么要拆成多张表？

音轨描述文件本身，分析表描述一次分析任务，特征表保存算法结果，分类表保存分类器版本和说明。拆表能减少概念混杂，并能通过外键表达关系。删除分析时利用级联规则清理依赖数据。

### 14. 数据写到一半程序出错怎么办？

新分析的四张业务表在同一事务中写入，任何一步出错都会整体回滚。导入使用每条记录一个 SAVEPOINT，一条错误只回滚这一条，不影响其他合法记录。

### 15. 如何处理重复音频和重复导入？

上传后先计算 SHA-256。相同文件字节具有相同指纹，系统直接返回原记录并删除新上传副本。导入时使用“文件哈希 + 原分析时间”识别同一导出记录，重复项会计入 skipped，不会反复膨胀数据库。

### 16. JSON、CSV 和数据库备份有什么区别？

- JSON 包含完整指标和可视化序列，可完整恢复结果。
- CSV 是 Excel 友好的扁平摘要，不保存嵌套曲线。
- SQLite 备份是数据库结构和数据的原生副本。

三者目前都不包含 `data/uploads` 中的原始 WAV，所以导入记录一般不能播放。

### 17. 为什么数据库备份不用直接复制 `.db` 文件？

程序运行时 SQLite 可能处于 WAL 模式，直接复制主文件可能遗漏尚未合并的日志页。项目使用 SQLite 官方连接备份接口生成一致副本，更适合在服务运行期间下载。

### 18. 长音频如何控制性能？

系统最多分析前 180 秒，内部采样率限制到不高于 11025 Hz；频谱最多抽取 140 帧，音高最多抽取 56 帧；波形约 600 个桶，能量和起音曲线最多 420 点。这些限制使纯 Python 分析和数据库传输保持可控，并通过 `truncated` 字段说明是否截断。

### 19. 系统如何保护本地数据？

程序强制只监听 `127.0.0.1` 或 `localhost`，不会上传互联网，也拒绝跨站写操作。服务端还限制文件大小、净化文件名、阻止静态目录穿越、使用参数化 SQL，并设置基本安全响应头。

### 20. 7 项测试分别覆盖什么？

4 项音频测试覆盖 440 Hz A4、完整演示特征、损坏 WAV，以及静音不崩溃并分类为“静音或近静音”；2 项数据库测试覆盖插入/导入/去重/删除闭环及 SQLite 备份；1 项服务器测试覆盖健康检查、演示生成、详情读取、JSON 导出和 Range 音频播放，其中 `bytes=0-99` 必须返回 HTTP 206、100 字节及 RIFF 文件头。测试资源均在临时目录生成，不依赖外部音乐文件。

### 21. 项目最大的亮点是什么？

不是单独做了某一个算法，而是实现了完整、可验证的闭环：零依赖 PCM 分析、四种图表、可解释分类、规范化 SQLite 模型、完整导入导出以及 7 项自动测试。内置理论值明确的合成音频和静音边界样例使算法能够重复演示和验证。

### 22. 下一步最值得增加什么？

第一步是可选接入 FFmpeg，支持 MP3、M4A 和 FLAC；第二步是用 NumPy 加速；第三步是准备带标签数据集，用 MFCC、频谱和节奏特征训练分类模型，并用独立测试集报告准确率。还可增加批量分析和包含原始音频的便携 ZIP。

## 五、现场故障备用方案

### 浏览器没有自动打开

查看启动窗口中的“访问地址”，手动输入浏览器。默认通常为：

```text
http://127.0.0.1:8765
```

### 8765 端口被占用

程序会自动选择空闲端口。也可以执行：

```powershell
python app.py --port 0
```

### 手头音频无法上传

确认扩展名为 `.wav` 且内部编码是未压缩 PCM。现场直接点击“生成演示音频”，不要临时转换大型 MP3。

### 分析耗时超出预期

使用内置约 12 秒演示音频。不要现场上传接近 180 秒或 80 MB 上限的文件。

### 图表没有显示

完整 JSON 和本地分析记录应包含图表序列；CSV 导入记录本来就不包含这些序列。切换到一条本地分析或完整 JSON 导入的记录。

### 数据库中没有历史记录

生成一次内置演示即可自动入库。概览、历史列表和分类统计会同步刷新。

### 老师要求证明不是写死结果

先展示内置 120 BPM 演示，再上传另一个 PCM WAV 比较 BPM、响度和频谱；或者打开 `test_440_hz_tone_is_detected_near_a4`，说明测试在运行时合成 440 Hz，而不是读取固定结果。
