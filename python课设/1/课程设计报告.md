## 摘要

随着数字音乐数量不断增加，仅依靠人工试听难以快速了解音频的节奏、音高、响度和频谱结构。本课程设计实现了一套名为 MusicScope 的本地音乐特征分析系统。系统采用浏览器作为图形用户界面，以 Python 标准库实现 HTTP 服务、PCM WAV 解码、数字信号处理和 SQLite 数据持久化，不依赖第三方 Python 包或云端接口。

系统支持导入 8/16/24/32 位未压缩 PCM WAV，对音频执行声道混合、箱式低通降采样、分帧和加窗，提取 BPM、调性、主导基频、音名、RMS dBFS、峰值、动态范围、频谱重心、85% 频谱滚降点和过零率等指标。节奏由短时能量起音包络的自相关估计，音高由归一化自相关估计，频谱由自主实现的 Cooley-Tukey FFT 计算，调性通过 Chroma 与 Krumhansl-Schmuckler 大小调模板匹配获得。系统进一步融合节奏、响度、频谱重心和动态范围，输出带文字依据的听感倾向分类。

全部分析结果、分类说明和绘图序列均保存至 SQLite。系统提供历史查询、分类筛选、结果恢复和级联删除，并实现完整 JSON、CSV 摘要、SQLite 备份以及 JSON/CSV 导入。测试使用程序生成的音频和临时数据库，共设置 7 项自动化测试，覆盖 440 Hz 音高、完整特征、错误文件、静音边界、数据库往返、备份和带 Range 播放断言的 HTTP 端到端流程，测试全部通过。

**关键词：** Python；音乐分析；数字信号处理；FFT；SQLite；Web 图形界面

## 1 绪论

### 1.1 课题背景

音频信号包含时间域和频率域两方面的信息。时间域波形能够反映声音振幅变化，频率域分析则能够描述音高、音色和频谱能量分布。节奏、音调和音量是用户理解音乐时最直观的三个维度，也是音乐信息检索、自动标注和内容推荐的基础。

传统命令行分析程序虽然能够输出数值，但不便于普通用户操作，也不能直接满足课程设计对图形界面、数据库持久化和文件导入导出的综合要求。因此，本项目把音频算法、Web 图形界面、数据库设计和软件工程测试整合为一个可离线运行的完整系统。

### 1.2 设计目标

本项目的主要目标如下：

1. 提供直观的图形用户界面，使用户无需输入命令即可完成音频分析。
2. 从 PCM WAV 中提取节奏、音调、音量和频谱等核心特征。
3. 使用图表展示波形、能量、频谱和十二音级分布。
4. 根据特征给出可解释的听感倾向分类。
5. 将所有分析指标和绘图序列保存到 SQLite 数据库。
6. 提供历史记录查询、筛选、查看和删除功能。
7. 支持数据库内容导出到文件以及从文件重新导入。
8. 尽量减少部署步骤，做到安装 Python 后即可一键启动。

### 1.3 设计原则

- **本地优先：** 音频分析在用户电脑完成，默认服务只监听 `127.0.0.1`。
- **零第三方依赖：** 后端只使用 Python 标准库，降低实验室电脑部署风险。
- **算法可解释：** 核心计算由源码实现，分类同时返回判断依据。
- **数据可恢复：** 指标和绘图序列写入数据库，历史图表无需重新分析。
- **功能闭环：** 输入、分析、展示、持久化、查询、导出和导入形成完整流程。

## 3 总体设计

### 3.1 系统架构

系统采用本地浏览器/服务器结构：

```text
用户浏览器
  │  HTML/CSS/JavaScript、Fetch、Canvas
  ▼
Python ThreadingHTTPServer
  ├─ REST API 与静态文件服务
  ├─ PCM WAV 分析模块
  └─ SQLite 数据访问模块
       │
       ├─ data/musicscope.db
       ├─ data/uploads/*.wav
       └─ data/exports/*.db
```

浏览器只负责交互和绘图；服务端负责文件检查、音频计算和数据库操作。该结构既满足图形界面要求，又避免引入桌面 GUI 或 Web 框架依赖。

### 3.3 核心业务流程

```text

  → 浏览器检查扩展名和 80 MB 上限

  → 服务端生成安全存储名
```

SQLite 随 Python 标准库提供，无需部署独立数据库服务，适合本地单用户课程设计。项目启用外键和 WAL 日志模式，并通过参数化 SQL 防止输入直接拼接到语句中。

一次新分析会依次写入 `tracks`、`analyses`、`features` 和 `classifications`。四次写入位于同一事务中，任一步骤异常都会回滚。

删除一条分析时，数据库外键级联删除特征和分类；没有其他分析引用的孤立音轨会被清理；服务端再删除 `data/uploads` 中对应的 WAV。

导入时每条记录使用 SAVEPOINT。某条数据不合法时仅回滚这一条，其他合法记录仍可提交。相同文件哈希和相同分析时间被视为同一导出记录并跳过。

## 5 音频分析算法

### 5.1 PCM 解码与预处理

`wave` 模块读取 WAV 头部和采样字节。不同位深按照各自满量程转换到近似 `[-1,1]`：

\[
x[n]=\frac{s[n]}{2^{B-1}}
\]

其中，\(B\) 为 16、24 或 32 位；8 位 PCM 是无符号数据，先减去 128 再除以 128。

多声道通过算术平均混合为单声道：

\[
x_m[n]=\frac{1}{C}\sum_{c=1}^{C}x_c[n]
\]

其中，\(C\) 为声道数。为控制纯 Python 运算量，内部分析采样率取原采样率与 11025 Hz 中的较小值，并在降采样区间做箱式低通平均以减少高频混叠。若多声道探测阶段发现算术平均发生明显反相抵消，则自动选用能量最高的声道。数据库仍保存原始采样率。

系统最多读取前 180 秒。分帧长度 \(N=1024\)，帧移 \(H=512\)。频谱分析前使用 Hann 窗：

\[
w[n]=0.5-0.5\cos\left(\frac{2\pi n}{N-1}\right)
\]

### 5.2 音量与动态范围

一帧或整段信号的均方根为：

\[
RMS=\sqrt{\frac{1}{N}\sum_{n=0}^{N-1}x^2[n]}
\]

数字满刻度相对响度为：

\[
L_{dBFS}=20\log_{10}(\max(RMS,10^{-10}))
\]

峰值 dBFS 使用最大绝对采样值代替 RMS。动态范围使用非静音帧响度的第 90 百分位减第 10 百分位：

\[
D=P_{90}(L)-P_{10}(L)
\]

项目直接对原始幅度计算这些量，没有先执行整体归一化，因此不同文件之间仍保留数字幅度差异。dBFS 是相对于数字满刻度的值，并非经过声学标定的声压级或 LUFS。

### 5.3 节奏 BPM

首先计算每帧 RMS，并转换为压缩后的对数能量：

\[
E_t=\log(1+100\cdot RMS_t)
\]

用当前能量相对上一帧及近期局部均值的正向增长构造起音包络：

\[
O_t=\max\bigl(0,E_t-\max(E_{t-1},\overline{E}_{t-8:t-1})\bigr)
\]

对归一化起音包络计算不同延迟下的自相关，在 55～200 BPM 对应的延迟范围内选择得分最高者。帧率为：

\[
f_{frame}=\frac{f_s}{H}
\]

因此：

\[
BPM=\frac{60f_{frame}}{lag}
\]

算法对常见的 75～160 BPM 设置轻微先验，用于减少半拍或双拍候选误选。若相关得分过低，则返回 BPM 为 0，界面显示未检测到稳定节拍。

### 5.4 基频、音高与音名

系统对通过能量门限的部分音频帧计算归一化自相关：

\[
r(\tau)=\frac{\sum_n x[n]x[n+\tau]}
{\sqrt{\sum_n x^2[n]\sum_n x^2[n+\tau]}+\varepsilon}
\]

在 55～1000 Hz 对应的延迟范围中选择可靠局部峰，基频为：

\[
f_0=\frac{f_s}{\tau_{best}}
\]

为了控制计算量，最多抽取 56 帧做基频估计；最终主导音高取有效帧频率的中位数。频率到 MIDI 音高的换算为：

\[
m=\operatorname{round}\left(69+12\log_2\frac{f_0}{440}\right)
\]

再根据 \(m\bmod 12\) 和八度得到 A4、C4 等音名。检测不到稳定基频时，频率为 0，音名显示“未知”。

### 5.5 FFT 与频谱特征

对加 Hann 窗后的帧执行 1024 点 Cooley-Tukey 快速傅里叶变换。离散傅里叶变换定义为：

\[
X[k]=\sum_{n=0}^{N-1}x[n]e^{-j2\pi kn/N}
\]

自主实现的基 2 FFT 将直接 DFT 的复杂度从 \(O(N^2)\) 降为 \(O(N\log N)\)。为保证长音频也能在纯 Python 环境运行，最多均匀抽取 140 帧用于平均频谱。

频谱重心为：

\[
C=\frac{\sum_k f_k|X[k]|}{\sum_k|X[k]|}
\]

它可近似描述声音的明亮程度。85% 频谱滚降点 \(f_r\) 满足：

\[
\sum_{f_k\le f_r}|X[k]|\ge 0.85\sum_k|X[k]|
\]

过零率为相邻采样发生符号变化的次数占比：

\[
ZCR=\frac{1}{N-1}\sum_{n=1}^{N-1}\mathbf{1}[x[n]x[n-1]<0]
\]

### 5.6 Chroma 与调性

系统把 55 Hz～5000 Hz 内的 FFT 频点换算为 MIDI 音高，再按 MIDI 编号对 12 取模累加到十二音级。累加权重为频谱能量除以频率平方根，用于减轻高频分量对调性的过度影响：

\[
Chroma[p] \mathrel{+}=\frac{|X[k]|^2}{\sqrt{f_k}},\quad p=MIDI(f_k)\bmod 12
\]

归一化 Chroma 分别与 12 个主音的大调模板和 12 个主音的小调模板计算 Pearson 相关系数，总计比较 24 个候选，取得分最高者作为调性。匹配度综合最佳相关值及其与第二名的差距。

### 5.7 规则分类

分类器版本为 `rules-1.0`，按以下顺序判断：

1. `RMS < -55 dBFS`：静音或近静音。
2. `BPM ≥ 125` 且 `RMS > -24 dBFS`：激情动感。
3. BPM 有效、`BPM < 85` 且 `RMS < -22 dBFS`：安静舒缓。
4. `频谱重心 > 2100 Hz`，且 BPM 未检测到或 `BPM ≥ 95`：明亮轻快。
5. `频谱重心 < 1250 Hz`，且 BPM 未检测到或 `BPM < 115`：温暖沉稳。
6. 其余情况：均衡流行。

基础匹配度分别从 0.95、0.78、0.80、0.76、0.74、0.70 开始；激情动感还会随 BPM 增加小幅提高。当动态范围大于 16 dB 时增加 0.03，最终不超过 0.95。

系统同时保存“节奏速度较快”“整体能量较强”等原因。该匹配度用于表示规则命中程度，不是机器学习概率，也不等同于专业音乐流派标签。

## 6 Web 服务与界面实现

### 6.1 HTTP 服务

服务器基于 `ThreadingHTTPServer`，每个请求可由独立线程处理。默认地址为 `127.0.0.1:8765`，端口冲突时自动选择空闲端口。主要接口如下：

| 方法 | 接口 | 功能 |
| --- | --- | --- |
| GET | `/api/health` | 健康检查、版本和支持格式 |
| GET | `/api/stats` | 数据概览统计 |
| GET | `/api/analyses` | 历史列表、搜索与分类筛选 |
| GET | `/api/analyses/{id}` | 查询完整记录及可视化序列 |
| GET | `/api/audio/{id}` | 播放仍在本地保存的 WAV |
| GET | `/api/export?format=json` | 下载完整 JSON |
| GET | `/api/export?format=csv` | 下载 CSV 摘要 |
| GET | `/api/database-backup` | 下载 SQLite 一致性备份 |
| POST | `/api/analyze` | 上传和分析 WAV |
| POST | `/api/demo` | 生成并分析内置演示音频 |
| POST | `/api/import` | 导入 JSON/CSV |
| DELETE | `/api/analyses/{id}` | 删除记录及本地 WAV |

### 6.2 前端实现

前端没有使用框架。`app.js` 通过 Fetch 调用 REST API，使用一个简单状态对象保存当前文件、当前记录、历史列表和统计信息。Canvas 根据数据库返回的压缩序列绘制四类图表，并在浏览器尺寸变化时重新绘制。

分析进度使用阶段提示改善长计算时的用户体验；实际完成以后才显示 100% 和“已保存到数据库”。所有来自文件名或数据库的文本在插入 HTML 前进行转义。

### 6.3 安全与边界检查

- 上传音频限制为 80 MB，导入文件限制为 25 MB。
- 文件名只保留末级名称，替换非法字符并限制长度。
- 静态资源解析后检查是否仍位于 `static` 目录，阻止目录穿越。
- 数据库查询使用参数占位符。
- JSON 禁止输出 NaN 和无穷值。
- 响应设置 `X-Content-Type-Options`、`X-Frame-Options` 和 `Referrer-Policy`。
- 默认只监听本机，音频不会发送给外部服务。

## 7 数据导入导出设计

### 7.1 JSON 完整数据

JSON 顶层包含应用名、数据库模式版本、导出时间、记录数和 `records` 数组。每条记录包含关系表查询得到的全部摘要字段，以及从 `feature_json` 还原的 `feature_data`。

JSON 使用 UTF-8 和中文原文，禁止 NaN。导入时检查模式版本；高于当前版本 1 的文件会被拒绝。完整 JSON 导入后可以恢复四类图表。

### 7.2 CSV 摘要

CSV 固定输出 32 个扁平字段，使用 UTF-8 BOM，便于 Microsoft Excel 正确显示中文。由于 CSV 不输出嵌套的 `feature_data`，重新导入后仅能查看摘要指标，图表会显示没有序列。

### 7.3 SQLite 备份

系统使用 `sqlite3.Connection.backup` 创建一致的数据库副本，而不是在运行中直接复制数据库文件。备份会保存到 `data/exports`，并同时作为下载响应发送给浏览器。

### 7.4 原始音频边界

JSON、CSV 和 SQLite 数据库备份不包含 `data/uploads` 中的原始 WAV 字节。导入的数据仍可查看指标；完整 JSON 可恢复图表，但不能试听。如果要完整迁移运行环境，应同时复制数据库和 `data/uploads`。

## 9 系统特点与不足

### 9.1 系统特点

1. 无第三方 Python 依赖，部署步骤少。
2. 从 PCM 解码、FFT 到自相关均可在源码中解释。
3. 音频分析、可视化、分类、数据库和导入导出形成完整闭环。
4. 内置可重复的 C 大调、120 BPM 演示素材，避免答辩依赖外部文件。
5. 保存绘图序列，历史结果无需重新分析。
6. 分类不伪装成黑盒模型，能够展示具体判断依据和版本。
7. 使用自动化测试验证理论音高、数据往返和端到端接口。

### 9.2 当前不足

1. 只直接支持未压缩 PCM WAV，MP3、M4A、AAC 和 FLAC 需先转换。
2. 纯 Python 算法速度和专业鲁棒性不及 NumPy、librosa 等优化库。
3. 节奏自相关可能产生半拍或双拍错误，对自由节奏和复节奏适应性有限。
4. 主导基频对单音和旋律明显的素材较有效，复杂多声部音乐可能不稳定。
5. 调性采用全局平均 Chroma，不能描述音乐中途转调。
6. dBFS 未进行感知响度加权，不等同于 LUFS。
7. 规则分类只表示听感倾向，不能替代经过标注数据训练的流派分类器。
8. JSON/CSV 和数据库备份没有包含原始 WAV；CSV 也没有可视化序列。

## 10 总结与展望

本课程设计完成了 MusicScope 音乐特征分析器。系统在纯 Python 标准库条件下实现了 PCM WAV 读取、预处理、节奏估计、基频检测、FFT 频谱、Chroma 调性、响度统计和规则分类，并使用原生 Web 页面完成数据展示。SQLite 模型把音轨、分析、特征和分类分离存储，通过事务和外键保证一致性；JSON、CSV、SQLite 备份及 JSON/CSV 导入满足了数据库内容与文件之间转换的课程要求。

测试结果表明，系统可以正确识别 440 Hz A4 测试信号，能够对内置音乐样例提取完整特征，能够安全处理并分类静音，也能完成数据库往返、HTTP Range 音频播放和端到端工作。项目达到了“有图形界面、有数据库、可导入导出、能够分析音乐特征并可视化和分类”的预期目标。

后续可从以下方向继续改进：

1. 可选接入 FFmpeg，扩展 MP3、M4A、AAC、FLAC 支持。
2. 使用 NumPy 加速长音频 FFT 和自相关，同时保留当前教学版实现。
3. 引入梅尔频谱、MFCC 和 LUFS 等特征。
4. 分段计算 BPM 与调性，展示随时间变化的结构。
5. 建立带标签数据集，训练并评估机器学习分类模型。
6. 导出包含数据库、JSON 和原始音频的便携 ZIP。
7. 增加批量分析、分页和分析任务取消功能。
